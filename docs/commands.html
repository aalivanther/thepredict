Administration

Commands & permissions

Everything /thepredict can do, who may run it, and how to read its answers.

There is one command, /thepredict, and /thepredict alone means /thepredict status. The command itself needs thepredict.admin, so a player without it can run no subcommand at all; the other permissions add to it. The console may run everything. Tab completion hides debug and duel from players without thepredict.debug.

The command also lists a few experimental subcommands that this documentation does not cover.

Tip nearest or a UUID

nearest picks the closest mob with a session within 16 blocks of you, so it needs a player. From the console, pass the entity UUID instead (/thepredict debug goals prints the full UUID, ready to copy).

#status

/thepredict status answers in fixed sections, always in the same order: Environment, Service, Catalog, Sessions, Encounters, Budget, Consumption, Latency (p50, p95, p99 of the last two minutes), Errors, Counters and Effectiveness, plus Storage when storage is running and a Patterns line. The whole answer never passes 48 lines: when there are more, the last one says <n> more status lines are not shown. It never shows the key and never names a player.

The lines you will read most:

#check

/thepredict check asks for a fresh service check without blocking the server. It answers Jev check started; the result arrives here without blocking the server. and later Jev check: <STATE> (<detail>). with the next step. The check calls GET /v1/models, which spends no tokens and does not test an inference. It uses the key read at startup: after changing the key, restart the server instead. If checks are already queued it answers Other checks are already waiting; see /thepredict status.

#inspect

/thepredict inspect <nearest|uuid> explains one bound mob in at most fourteen lines:

LineShows
Mob <id> generation <n>Which mob and which session.
SessionMythicMobs ID, profile, state, level and encounter.
IntentCurrent tactic, movement, choice, confidence, ticks left, whether its skill was tried, [debug] for a forced intent. Without one: none; level 4 runs the base AI of the goal set.
Next optionsAlternatives and contingencies of the last answer.
WhyLast fallback reason, last cast result and the low-confidence and no-progress streaks.
PerceptionHealth band, target distance and trend, reachable, visible, flankable, active contexts, eligible tactics, skills out of reach.
SkillsEach choice's delivery, reach, radius, wind-up, line of sight, cooldown class and origin (origin=skill when the Intention line was used), or untyped.
TargetThe target by alias (player_1, or entity_1 (zombie)), perceived participants and combat time.
EventsThe latest combat events.
Goalsinstalled for revision <n> or not installed (MythicMobs keeps its AI), and the goal set.
MovementProgress of the current movement.
ThreatThe native threat table and what ThePredict added.
OutcomesThe last 8 closed outcome windows, newest last.
AggregateWith the aggregates database: windows=… effect=… stored for the current tactic in a similar situation.

Add a detail word for one subsystem: tick (the per-tick reading of the target), stance, telegraph, group or patterns, in any case. There is no zone detail. A mob without a session answers <id> has no session: it is not a bound mob with Predictor: true and an active profile.

#intention suggest

/thepredict intention suggest [profile] prints, for each bound choice, the Intention line its skill should carry, in canonical order, plus what the line cannot express (for example a reach, which belongs in targetwithin). An untyped choice prints untyped; no Intention line. Without a profile ID it covers every bound profile. It never writes a MythicMobs file: copy the lines yourself (see Skills & intents).

#records

records stats answers at once with one line: <state> [cause] records <level> dropped <n> inFlight <n> failed <n> sqlite <version>. Every other records subcommand needs thepredict.records, is queued on the storage thread and answers queued; the result arrives later in your chat or console. Only one command of each kind runs at a time (A records command of that kind is already running.), and without a storage writer they answer Records <action> needs the storage writer.

  • export outcomes [profile] writes records/exports/outcomes-all.csv (or outcomes-<profile>.csv). It reads the aggregates database.
  • export events <from> <to> [types] takes UTC days as yyyy-MM-dd and writes records/exports/events-<from>-<to>.jsonl, optionally only some line types. It stops at 512 MiB and says capped.
  • prune [days] deletes record days older than days; today is never deleted.
  • verify runs SQLite's integrity check and answers ok or the first problem.
  • backup writes a copy into records/backups/ and keeps storage.backupsKept copies.
  • tag <tag> labels every following record line with [a-z0-9-]{1,40}; tag clear stops.

See Storage & records for what the records hold.

#eval

Changing soon

eval reads and tunes the target-time difficulty, which is about to be redefined as intelligence levels. It works as described here in the current build.

  • eval difficulty <nearest|uuid> shows two lines for one mob: preset <name> entropy <true|false> and r <ticks> c <seconds> pressure <rung>, where r is the current reaction delay, c the Entropy adaptation time and pressure the rung, bench at full power. A mob without a session answers no session.
  • eval status shows the same block for the nearest bound mob or, without one, the configured default preset at full power.
  • eval pressure <nearest|uuid> <0-8|auto> forces a pressure rung for testing; auto gives control back to the controller. It also needs thepredict.debug and is not stored.
  • eval verdict import <file> validates an evaluation verdict file and copies it into records/eval/verdicts/ (and the aggregates database). Modes waiting for a verdict, such as patterns.mode: bias, are re-offered at once, without a restart. <file> is a path inside the plugin folder, plugins/ThePredict/: relative to it (never to the folder the server starts from), or absolute inside it. A path with .. is refused with path; an absolute path outside the folder, or a link that leads out of it, with path: must stay inside the plugin folder. Nothing is imported then.
  • eval verdict list shows the loaded verdicts, one line each, at most 8 lines. Before the first load it answers pending: the verdicts have not loaded yet; with none, no verdict loaded.
  • eval report answers eval report is not available on the server in this release.

#zone

/thepredict zone prints one fixed line: No ready zone. Effective mode is the minimum of zone.mode and Zone.Mode. Permission: thepredict.admin. In this release neither zone nor inspect shows a mob's zone. See Zones & terrain.

#learn and autoconfig

/thepredict learn manages learning data and learned values; learn status prints one line, the rest is queued on the storage thread. See Learning & training. /thepredict autoconfig imports, shows, applies and reverts profile overlays. See Profile overlays.

#debug

Debug tools need thepredict.debug, which not even operators have by default. Without it, debug answers You need the thepredict.debug permission to use debug tools and neither debug nor duel shows up in tab completion. The console can always use them.

  • debug intent <nearest|uuid> <tactic> [ticks] sets a LOCAL intent with one tactic of the mob's profile, for 1 to 6000 ticks (without [ticks], the profile's intent length: 40 ticks by default). It never sends a request to Jev. It refuses, with the reason, a tactic the profile does not declare or that was not eligible at the last capture (a context that does not allow it, a skill on cooldown, no target, or FLANK without a raised shield).
  • debug release <nearest|uuid> drops the mob to level 4; the fallback chain decides again within 2 ticks.
  • debug goals <nearest|uuid> prints the full UUID and generation, one line per goal (running while it runs) and the movement progress.

#duel

/thepredict duel records, in real time, a fight between two factions of mobs. It is off until you start it and costs nothing while idle. It needs thepredict.debug (without it: You need the thepredict.debug permission to record duels).

Console
/thepredict duel start <label> <factionA> <factionB> [radius] [skills=A,B]
/thepredict duel start <label> <factionA> <factionB> <world> <x> <y> <z> [radius] [skills=A,B]
/thepredict duel status
/thepredict duel stop
  • The first form is for players: the arena is centred on you, in your world. The console must use the second form with a loaded world and coordinates.
  • label matches [a-z0-9-]{1,40}. factionA is the red side and factionB the blue one; they must differ.
  • The radius defaults to 24 blocks, at most 64. skills= lists the skills that count as casts; by default, the MythicMobs skill choices of the bound profiles whose Entities.Allow names one of the two factions.
  • start answers Duel recording '<label>' started: red = <A>, blue = <B>, radius <r>, folder <folder>; stop writes summary.md and says how many rounds and dropped rows there were.

What the recorder writes is described in Storage & records.

#Permissions

PermissionDefaultGrants
thepredict.adminopThe /thepredict command itself (a player without it can use no subcommand), plus status, check, inspect, intention suggest, zone, records stats and learn status.
thepredict.recordsop/thepredict records except stats: export, prune, verify, backup, flush, cache and tag.
thepredict.evalop/thepredict eval: status, difficulty, report and verdicts. pressure also needs thepredict.debug.
thepredict.learnop/thepredict learn build, export, import, rollback and disable (status also accepts thepredict.admin).
thepredict.autoconfigop/thepredict autoconfig: status, import, show, apply and revert.
thepredict.debugfalse/thepredict debug (set, release and list local intents; never sends a request to Jev) and /thepredict duel. Not even operators have it by default; the console always does.

Every subcommand also needs thepredict.admin, the permission of the command itself. thepredict.admin alone is enough for records stats and learn status.

To give the debug tools to operators without a permissions plugin, create permissions.yml in the server root:

permissions.ymlYAML
thepredict.verifier:
  description: Grants ThePredict debug tools to operators on the verification server
  default: op
  children:
    thepredict.debug: true
